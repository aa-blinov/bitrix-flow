# Архитектура

Как устроен bitrix-flow и почему решения приняты именно так. Документ для того, кто
собирается менять код; пользовательские команды и ловушки лежат в
[../AGENTS.md](../AGENTS.md), продуктовая рамка в [../PRODUCT.md](../PRODUCT.md).

## Слои

Приложение это Next.js 16 (App Router, React 19), MongoDB 7 и Caddy в Docker Compose.
Код разделён на четыре слоя.

| Слой                  | Где                                                      | Ответственность                                            |
| --------------------- | -------------------------------------------------------- | ---------------------------------------------------------- |
| Страницы и API        | `src/app/`                                               | Маршруты App Router, route handlers, серверные страницы.   |
| Клиентские компоненты | `src/components/`, `src/hooks/`, `src/store/`            | Доска, карточка, фильтры, уведомления, состояние Zustand.  |
| Серверная логика      | `src/lib/`                                               | OAuth, сессии, MongoDB, зеркало задач, общение с Bitrix24. |
| Инфраструктура        | `scripts/`, `caddy/`, `Dockerfile`, `docker-compose.yml` | Сборка, бэкапы, проверки, прокси.                          |

`src/app/(dashboard)/` это группа маршрутов с общим сайдбаром: главная, мои задачи,
все задачи, проекты, сводка, нагрузка, уведомления, поиск. `src/app/api/` содержит
REST и SSE. `src/proxy.ts` перехватывает запросы до страниц и API и проверяет
сессионную куку.

`src/lib/mongo.ts` работает только на сервере. Клиентские компоненты не импортируют
его и не обращаются к MongoDB напрямую: они ходят в `/api/*`. Это граница, которая
не даёт строке подключения и OAuth-токенам попасть в браузерный бандл.

## Вход через OAuth

Вход устроен как обычное приложение Bitrix24, установленное на портал.

1. `/api/oauth/start` генерирует `state`, кладёт его в HttpOnly-куку
   `bitrix-oauth-state` на 10 минут и уводит на `oauth.bitrix.info`. Область доступа
   по умолчанию: `tasks,sonet_group,user,calendar,im,crm,disk`.
2. `/api/oauth` принимает callback с `code`, сверяет `state`, если он ожидался, и
   меняет код на токены. Bitrix24 в маркетплейс-сценарии может не присылать `state`,
   поэтому проверка выполняется только при наличии сохранённого значения.
3. Токены, `member_id`, домен портала и `application_token` сохраняются в коллекцию
   `user_tokens`. Домен берётся из `client_endpoint`, а не из `domain` ответа OAuth:
   OAuth-сервер возвращает свой хост, а для REST нужен хост портала.
4. После обмена приложение подписывается на `OnTaskAdd`, `OnTaskUpdate`,
   `OnTaskDelete` и `OnTaskCommentAdd` через `event.bind`. Адрес обработчика
   собирается из `BITRIX24_APP_URL`, а не из заголовка `Host`: подменённый `Host`
   иначе привязал бы события портала к чужому адресу.
5. `/install` обслуживает прямую установку из маркетплейса. Если пришёл `AUTH`,
   токен сохраняется, и браузер уходит на главную с `install=success`.

`/api/oauth/check` отвечает, есть ли живая сессия и подключённый портал. Он нужен
сайдбару и странице `/connect`, чтобы отличить «нет входа» от «вход есть, а портал
не подключён».

## Сессия и доступ

Пользователь входит по `AUTH_USERNAME` и `AUTH_PASSWORD`. Пароль сравнивается через
`timingSafeEqual`, на IP действует лимит: пять неудачных попыток за 15 минут, потом
ответ 429.

Успешный вход выдаёт куку `bitrix-kanban-session` на 8 часов. В куке лежит
base64url-полезная нагрузка с `sessionId` и `expiresAt`, подписанная HMAC-SHA256
ключом `AUTH_SESSION_SECRET`. На сервере в коллекции `sessions` хранится SHA-256 от
`sessionId`, а не сам идентификатор, с TTL-индексом на `expiresAt`. Выход удаляет
запись, поэтому украденная кука перестаёт работать сразу, а не через восемь часов.

`getAuthorizedMemberId` принимает только живую серверную сессию и выбирает токен
портала сам. Браузер не может передать произвольный `member_id` и получить чужой
портал: установка рассчитана на один защищённый портал, и выбор токена по заголовку
был бы IDOR, как только в базе появится второй.

`src/proxy.ts` пропускает без сессии только `/login`, `/api/auth/login`,
`/api/auth/logout`, `/api/b24/handler`, `/api/oauth`, `/api/oauth/check`, `/install` и
`/api/health`. Остальные страницы уводят на `/login` с параметром `next`, остальные
API отвечают 401.

## Зеркало в MongoDB

Bitrix24 остаётся источником правды. Приложение держит зеркало, чтобы списки и
карточки не зависели от скорости портала.

| Коллекция                                                               | Что хранит                                                       |
| ----------------------------------------------------------------------- | ---------------------------------------------------------------- |
| `user_tokens`                                                           | OAuth-токены портала и `application_token`.                      |
| `task_mirror`                                                           | Полный снимок задачи в поле `data`, ключ `(member_id, id)`.      |
| `tasks`                                                                 | Свежие записи фонового синка, перекрывают `task_mirror` по `id`. |
| `task_sync_jobs`                                                        | Очередь точечных обновлений после событий.                       |
| `notifications`                                                         | Лента уведомлений, TTL 30 дней.                                  |
| `events_stream`                                                         | Поток для SSE, TTL 2 дня.                                        |
| `sessions`                                                              | Хэши сессий, TTL 8 часов.                                        |
| `cache`, `projects`, `stages`, `comments`, `time_entries`               | Кэш и справочники.                                               |
| `task_views`, `task_grid_preferences`                                   | Сохранённые виды и раскладка колонок.                            |
| `project_summary_snapshots`                                             | Снимок сводки проектов и признак устаревания.                    |
| `workload_time_aggregate`, `workload_time_task`, `workload_time_status` | Агрегаты учёта времени для нагрузки.                             |

Фоновый синк запускается из `src/instrumentation.ts` при старте сервера. Он проходит
раз в 60 секунд, первый проход через 15 секунд после старта. Запрос идёт по
`filter[>=CHANGED_DATE]` с перехлёстом окна в 2 минуты, страницами по 50 задач, не
больше 20 страниц за проход. Перехлёст нужен потому, что задача, изменённая во время
прохода, иначе не попала бы ни в текущий проход, ни в следующий.

Удаление даты не меняет, поэтому раз в 10 минут синк сверяет состав задач с порталом
и удаляет из `task_mirror` и `tasks` записи, которых в Битриксе больше нет. Вебхук
`OnTaskDelete` делает то же самое точечно, но он может потеряться, а задача,
удалённая пока сервер лежал, иначе осталась бы навсегда.

Обновление одной задачи идёт через `task_sync_jobs`. Воркер захватывает задачу
атомарно, ставит блокировку на 60 секунд и обновляет `task_mirror`. При ошибке
делается до восьми попыток с задержкой `min(300 s, 2^attempts)`, после чего запись
получает статус `failed`. Очередь разбирается и по таймеру `mongo.ts`, и сразу после
события.

`task_mirror` хранит полный ответ `tasks.task.get`, включая чек-листы.
Список читает только нужные поля. Теги запрашиваются отдельным вызовом: `tasks.task.get`
без `select` их не отдаёт, а с `select` отдаёт только их, поэтому оба запроса идут
параллельно.

## Приём событий

`POST /api/b24/handler` это публичный обработчик Bitrix24.

1. Тело принимается как JSON или как form-data, вложенные ключи вида `data[FIELDS_AFTER][ID]`
   разворачиваются в объект.
2. Событие и `member_id` обязательны. `application_token` сверяется с сохранённым
   через `timingSafeEqual`. Если токена в базе ещё нет, а событие пришло в течение
   часа после установки, токен подхватывается: так работают установки, сделанные до
   появления проверки. Без совпадения обработчик отвечает 403.
3. Событие обогащается: для комментария подтягивается текст из чата задачи
   (`im.dialog.messages.get`), для остальных событий заголовок задачи.
4. Уведомление пишется в `notifications`. Дубликат с тем же `messageId` не создаёт
   вторую карточку, а обновляет существующую.
5. Запись уходит в `events_stream`, кэш `memberId:` сбрасывается, сводка помечается
   устаревшей, старая запись задачи удаляется из `tasks`, а в `task_sync_jobs`
   ставится задание.
6. Bitrix24 сразу получает `{ "status": "ok" }`. Точечное обновление зеркала
   выполняется в `after()`, после ответа, чтобы один вебхук не запускал обход всего
   портала и не упирался в таймаут.

`POST /api/b24/register-handler` повторяет подписку на те же четыре события вручную.
Он не принимает URL обработчика от клиента: адрес всегда собирается из
`BITRIX24_APP_URL`, иначе приложение можно было бы превратить в пересыльщик событий
на чужой адрес.

## SSE

`GET /api/events` отдаёт `text/event-stream`. Перед подтверждением соединения сервер
запоминает последний `_id` в `events_stream` для этого `member_id`, поэтому событие,
пришедшее в момент подключения, не теряется. Дальше раз в секунду читаются новые
записи, не больше десяти за раз, и каждые 30 секунд уходит комментарий-сердцебиение.
Историю лента берёт из `/api/notifications`, а не из потока.

На клиенте `src/hooks/useSSE.ts` держит одно соединение на `member_id` и раздаёт
события подписчикам. Раньше каждый вызов хука открывал свой `EventSource`, и на
странице проекта их было два, а на сводке три. Состояние связи (`connecting`,
`online`, `offline`) показывается отдельно, чтобы вкладка не жила молча со старым
списком.

## Доска и чтение

Страницы доски это клиентские компоненты. Фильтры, группировка и сортировка живут в
URL, поэтому ссылку на вид можно сохранить и передать. `TaskGrid` умеет канбан и
список, перетаскивание стадий на `@dnd-kit`, сохранённые виды и настройки колонок.

`GET /api/tasks/all` не ходит в Bitrix24 на каждый запрос. Он собирает данные
агрегацией MongoDB: `task_mirror` объединяется с более свежими `tasks` через
`$unionWith`, записи дедуплицируются по `id`, поля нормализуются (оба регистра
ключей, строковые часы в числа, теги в массив названий). Фильтры, сортировка,
группировка и пагинация выполняются на сервере, поэтому группа «Иван (12)» означает
12 задач во всём списке, а не 12 на текущей странице.

Полный обход портала остаётся только на холодном старте, когда зеркала ещё нет.
Поиск ограничен 200 символами и экранируется: длинная строка иначе превращалась бы
в полный скан регулярным выражением. Страница не больше 100 задач, по умолчанию 50.

`/api/workload/summary` считает ячейки недельного календаря по всему зеркалу, а не по
первой странице списка. `/api/projects/summary` собирает план и факт по проектам;
план считается по листьям дерева задач, чтобы оценка родителя не удваивалась.
`/api/workload/time` отдаёт агрегаты учёта времени, которые обновляет планировщик
`workload-time-scheduler.ts`.

## Общение с Bitrix24

Все REST-вызовы идут через `src/lib/bitrix-request.ts`, а не через голый `fetch`.

Портал публикует несколько AAAA-записей и несколько A-адресов, часть которых висит
на подключении. Запросы принудительно идут по IPv4, а адреса перебираются группами:
соединение ждём 2 секунды, ответ до 30 секунд. Чтения можно гонять по трём адресам
параллельно, мутации только по одному: повтор POST на другом адресе создал бы вторую
задачу или комментарий. Адрес, который не ответил, помечается мёртвым на 30 минут.

`getBitrixFileStream` скачивает вложения тем же перебором адресов, но потоком и по
одному адресу, чтобы не тянуть файл дважды.

## Мессенджер

Страница `/messenger` показывает чаты Битрикс24 того пользователя, от чьего имени
установлено приложение: личные, группы проектов (`SONET_GROUP`), обсуждения задач
(`TASKS_TASK`) и прочие чаты. Данные идут через `/api/messenger/dialogs` и
`/api/messenger/messages` (GET читает, POST отправляет, PATCH отмечает прочитанным),
а не через прокси задач: методы `im.*` не добавляются в его белый список, чтобы
сессия не открывала весь мессенджер портала. Идентификатор диалога проверяется
регуляркой `DIALOG_ID` из `src/lib/messenger.ts`: число для человека или `chat<число>`.

В MongoDB сообщения не хранятся, Битрикс остаётся источником правды. События о
сообщениях портал обычному приложению не присылает (они есть только у чат-ботов),
поэтому список диалогов опрашивается раз в 15 секунд, открытая переписка раз в 5, и
только пока вкладка видна. Листание устроено по курсорам портала: диалоги по `OFFSET`
с шагом в размер страницы (страницы `im.recent.list` перекрываются, поэтому клиент
склеивает их по id), история по `LAST_ID` (старше) и `FIRST_ID` (ближайшие новее), так
что опрос тянет только новое и не затирает подгруженную историю. Отправка идёт одним адресом без повтора, как и остальные
мутации.

Прочитанность приходит вместе с сообщениями: `im.dialog.get` отдаёт `readed_list`
(у каждого участника id последнего прочитанного им сообщения), и своё сообщение
считается прочитанным теми, чей id не меньше его. Поля нет в документации метода,
но портал отдаёт его для личных чатов и групп. Вызов идёт параллельно с историей,
а его сбой не роняет сообщения.

Текст сообщения читается и тегами Битрикса (`[B]`, `[URL]`, `[USER=9 REPLACE]`), и
Markdown (`src/lib/message-markdown.ts`): блоки кода, цитаты, списки, заголовки,
жирный, курсив, зачёркнутый, ссылки и голые адреса. Теги разбираются первыми, поэтому
дефис после `[USER=1]Имя[/USER]` не становится маркером списка. Markdown включается
флагом `markdown` у `BitrixText`: в задачах и комментариях текст остаётся как есть.

Вложения идут через свои роуты, а не ссылками портала: те ведут на страницу входа без
cookie портала. `GET /api/messenger/file?dialogId&fileId` просит у портала подписанную
ссылку `im.v2.File.download` (он проверяет, что пользователь состоит в чате) и стримит
файл через `getBitrixFileStream` с поддержкой `Range`, без которого Safari не играет
звук и видео. `POST /api/messenger/files` принимает multipart (до 20 МБ), кодирует файл
в base64 и зовёт `im.v2.File.upload`: файл и сообщение с ним создаются одним вызовом,
отдельным `im.message.add` файл не отправить. Карточки-вложения (`params.ATTACH`) от
ботов и мониторингов рисуются блоками: текст, поля, ссылки.

События в реальном времени: портал отдаёт их обычному приложению через `im.v2.Event.get`
(подписка `im.v2.Event.subscribe`, очередь подтверждается по `offset`). Поллер
`src/lib/messenger-events.ts` работает только пока открыта хотя бы одна вкладка (число SSE-
подписчиков берёт из `/api/events`), читает очередь раз в три секунды и кладёт события в
`events_stream`, откуда их раздаёт тот же SSE, что и события задач. Портал присылает каждое
событие дважды, поэтому повторы отбрасываются, а события старше двух минут (очередь после
перезапуска) не показываются. Без вкладок подписка снимается через 90 секунд, чтобы портал не
копил очередь сутки. Клиент по событию перечитывает нужный диалог, а опрос оставляет редким.

Фото и видео открываются в `FileViewer`: полноэкранная панель с листанием по всем медиа
диалога, увеличением и скачиванием; остальные форматы это ссылка на тот же роут с
`download=1`. Пункты левого меню переставляются через `@dnd-kit` (`SortableNav`),
порядок хранится в `localStorage`, как и недавние проекты.

Голосовые записываются в браузере (`MediaRecorder`) и уходят тем же роутом файлом
«Голосовое сообщение ….ogg|m4a|webm». Признак голосового сообщения REST-приложение
выставить не может, поэтому в самом Битриксе запись видна обычным аудиофайлом с
плеером, а Chrome пишет webm, и портал считает его видео. В нашем плеере запись
узнаётся по имени.

## Деплой

`Dockerfile` собирает Next.js в standalone-режиме на `node:20-alpine` в три стадии:
зависимости, сборка, запуск. Секрет Sentry передаётся build-секретом, а не `ARG`,
поэтому не остаётся в истории слоёв.

`docker-compose.yml` поднимает приложение, MongoDB 7 и Caddy. У MongoDB нет проброса
порта на хост. Сервисам заданы фиксированные адреса в подсети `172.32.10.0/24`:
встроенный DNS Docker иногда переставал резолвить имена контейнеров, и Caddy ходил
по адресу, а не по имени. Healthcheck приложения дергает `/api/health`, который
пингует MongoDB, поэтому `healthy` означает, что приложение действительно видит базу.

Caddy terminates TLS через DuckDNS и добавляет HSTS, `nosniff`, `Referrer-Policy` и
`frame-ancestors`, разрешающий встраивание только своему origin и порталам Bitrix24.
Для `/api/events` отключена буферизация (`flush_interval -1`), иначе SSE не доходил
бы до браузера.

## Границы

- Компоненты не импортируют `src/lib/mongo.ts`, `oauth-client.ts` и другие серверные
  модули. Только через `/api/*`.
- Все вызовы Bitrix24 идут через `bitrix-request.ts`, чтобы таймауты, IPv4 и обход
  мёртвых адресов работали одинаково.
- Новые сущности, которых нет в Bitrix24, не заводятся. Исключение это служебные
  вещи вроде сохранённых видов и настроек грида.
- Битрикс главный. Любая запись сначала уходит в портал, потом в зеркало. Если данные
  расходятся, прав портал.
- Установка рассчитана на один портал. Выбор `member_id` из браузера запрещён.

## Открытые вопросы

- Нужна ли локализация кроме русского, не решено.
- Насколько важна мобильная версия, не решено. Сейчас интерфейс адаптивный, но
  отдельного мобильного клиента нет.
